# Виявлення таблиць ACPI в UnityKernel

У цьому документі описано початкову підтримку ACPI в UnityKernel, використання
поточного API, його обмеження та рекомендований порядок реалізації наступних
можливостей ACPI.

## Поточна підтримка

UnityKernel отримує інформацію ACPI через протокол Multiboot2:

1. UnityBoot переглядає теги Multiboot2 та шукає `AcpiOld` і `AcpiNew`.
2. Якщо присутні обидва теги, зберігається RSDP версії ACPI 2.0 або новішої
   з `AcpiNew`.
3. UnityBoot передає адресу RSDP і розмір даних тегу ядру через
   `UnityBootProtocol::BootInfo`.
4. Під час запуску ядра `Driver::ACPI::initialize()` перевіряє контрольні
   суми RSDP і знаходить RSDT або XSDT.

Реалізація ACPI розташована в `portable/drivers/acpi/acpi.cpp`, а публічні
оголошення — в `include/drivers/acpi/acpi.hpp`. Це джерело компілюється як
частина цілі ядра.

Поточна реалізація вміє:

- Перевіряти сигнатуру RSDP і базову контрольну суму.
- Перевіряти розширену контрольну суму RSDP для ACPI 2.0 або новішої версії.
- Знаходити RSDT або XSDT, перевіряти контрольну суму та формат записів
  таблиці System Description Table (SDT), а також повертати кореневу таблицю
  через `rootTable()`.
- Шукати записи в кореневій таблиці за чотирисимвольною сигнатурою та
  повертати таблицю лише за умови, що її контрольна сума SDT правильна.

Це лише пошук таблиць. Реалізація не інтерпретує AML, не перелічує ACPI-пристрої,
не налаштовує контролери переривань і не виконує керування живленням через ACPI.

## Використання API

Публічний API розташований у просторі імен `Driver::ACPI`:

```cpp
#include <drivers/acpi/acpi.hpp>

if (Driver::ACPI::isInitialized()) {
    const auto* madt = Driver::ACPI::findTable("APIC");
    if (madt != nullptr) {
        const auto* tableData =
            reinterpret_cast<const uint8_t*>(madt) + sizeof(*madt);
        const uint32_t tableDataSize = madt->length - sizeof(*madt);

        // Розбирайте `tableData`, використовуючи `tableDataSize` байтів.
    }
}
```

`"APIC"` — сигнатура Multiple APIC Description Table (MADT). Повернений
вказівник посилається на пам'ять, надану прошивкою, і призначений лише для
читання. Загальний заголовок SDT описано структурою `SystemDescriptionTable`;
специфічні для таблиці дані починаються одразу після цього заголовка. Для
обмеження читання цих даних завжди використовуйте поле SDT `length`.

`initialize(rsdp, rsdpSize)` повертає `true`, лише якщо знайдено придатну
кореневу таблицю. Під час запуску ядро повідомляє про успішну ініціалізацію
або виводить попередження, якщо ACPI відсутня чи некоректна. `findTable()`
повертає `nullptr`, якщо ACPI не ініціалізована, сигнатура дорівнює `nullptr`
або таблиці з такою сигнатурою немає.

## Обмеження адресації та безпеки

Зараз ядро збирається для 32-бітного x86. Адреси ACPI від прошивки є
фізичними адресами, але ця реалізація наразі трактує їх як вказівники, за
якими можна напряму читати. Це працює лише тоді, коли відповідна пам'ять ACPI
відображена identity mapping і доступна ядру. 64-бітну адресу XSDT, яка не
вміщується в `uintptr_t`, використати неможливо; у такому разі реалізація
пробує скористатися RSDT, якщо вона доступна.

Перш ніж використовувати ACPI на інших машинах, реалізуйте відображення
фізичної пам'яті та перетворюйте фізичні адреси прошивки через цей механізм.
Використовуйте його для таблиць ACPI та регістрів APIC, відображених у
пам'ять. Перевіряйте адресні діапазони та довжини за картою фізичної пам'яті.

UnityBoot не копіює та не резервує таблиці ACPI. Під час створення менеджера
фізичної пам'яті потрібно врахувати час життя таблиць і резервування їхньої
пам'яті.

## Рекомендований план реалізації

### 1. Розібрати MADT

Використовуйте `findTable("APIC")` і обходьте записи змінної довжини після
загального заголовка SDT. Кожен запис починається з типу та довжини; відхиляйте
записи, коротші за мінімальний розмір відповідного типу, з нульовою довжиною
або такі, що виходять за межі MADT.

Спочатку підтримайте щонайменше:

- Записи Local APIC для процесорів.
- Записи I/O APIC.
- Перевизначення джерел переривань (Interrupt Source Override).
- Перевизначення адреси Local APIC.
- Записи NMI Local APIC, якщо вони потрібні.

Невідомі типи записів варто пропускати за перевіреною довжиною, щоб новіші
записи прошивки не ламали розбір. Відокремте розбір від ініціалізації
обладнання та тестуйте його на синтетичних буферах MADT.

### 2. Додати доступ до фізичної пам'яті

Перш ніж розіменовувати таблиці прошивки за межами поточної identity-mapped
області, створіть інтерфейс відображення фізичних адрес. Використовуйте його
для таблиць ACPI та регістрів APIC, відображених у пам'ять. Перевіряйте
діапазони адрес і довжини за картою фізичної пам'яті.

### 3. Ініціалізувати маршрутизацію переривань APIC

Після розбору та відображення MADT:

1. Визначте підтримку APIC процесором і за потреби ввімкніть Local APIC.
2. Відобразіть та ініціалізуйте I/O APIC.
3. Враховуйте перевизначення джерел переривань з MADT під час вибору
   векторів переривань.
4. Налаштуйте маскування та маршрутизацію переривань.
5. Перевірте переривання таймера та клавіатури, перш ніж покладатися на
   маршрутизацію APIC у звичайній роботі ядра.

Для цього також потрібні працездатні IDT та інфраструктура обробників
переривань. Не замінюйте поточну конфігурацію контролерів переривань, доки
шлях APIC не буде перевірений.

### 4. Додати FADT та керування живленням

Використовуйте `findTable("FACP")`, щоб знайти Fixed ACPI Description Table
(FADT). Спочатку реалізуйте лише потрібні інтерфейси фіксованого обладнання.
Інтерпретатор AML — це окрема значно більша можливість; наявність FADT не
означає, що інтерпретація AML вже підтримується.

### 5. Покращити перевірки та тестування

Додайте цільові тести для коректних і некоректних RSDP, вибору RSDT/XSDT,
помилок контрольних сум, некоректних записів кореневої таблиці та пошуку
таблиць. Доступ до фізичної пам'яті має бути схований за інтерфейсом, який
можна тестувати без розіменування реальних адрес прошивки.
