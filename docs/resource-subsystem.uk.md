# ResourceSubsystem

## Огляд

`ResourceSubsystem` — це підсистема ядра UnityKernel, яка забезпечує централізований реєстр ресурсів. Вона надає ресурсам унікальні ідентифікатори та зберігає метадані, потрібні іншим компонентам ядра для ідентифікації ресурсів і отримання інформації про них.

Підсистема **не виконує операцій із ресурсами та не керує їхньою внутрішньою реалізацією**. Вона лише зберігає інформацію про зареєстровані ресурси.

## Основні обов’язки

`ResourceSubsystem` відповідає за:

- призначення ідентифікаторів зареєстрованим ресурсам;
- зберігання метаданих ресурсів;
- отримання переліку зареєстрованих ресурсів;
- надання інформації про тип і можливості ресурсу;
- зберігання інформації про драйвер, який створив ресурс;
- зберігання та зміну інформації про драйвер, який наразі відповідає за його обслуговування;
- видалення записів ресурсів із реєстру.

Підсистема не зобов’язує всі компоненти ядра використовувати її. До неї звертаються лише ті компоненти, яким потрібні спільні ідентифікатори або метадані ресурсів.

## Поняття ресурсу

Ресурс — це сутність ядра, якій потрібні спільний ідентифікатор та/або метадані для взаємодії з іншими компонентами системи.

Ресурсом може бути, наприклад:

- фізичний пристрій;
- блоковий пристрій;
- віртуальний пристрій;
- ресурс, створений одним драйвером на основі іншого драйвера;
- внутрішні дані або об’єкт ядра, для якого потрібна спільна ідентифікація.

Не кожен об’єкт ядра обов’язково має бути ресурсом. Реєструвати потрібно лише ті сутності, для яких така ідентифікація справді потрібна.

## Ідентифікатор ресурсу

```cpp
using ResourceID = int32_t;
```

`ResourceID` — це ідентифікатор, за яким ресурс знаходять у реєстрі.

Ідентифікатор можна зберігати в інших підсистемах або драйверах як посилання на запис ресурсу. Наприклад, драйвер файлової системи може зберігати `ResourceID` блокового пристрою, з яким він працює.

`ResourceID` не є вказівником на об’єкт ресурсу та сам по собі не надає доступу до його функціональності.

Після видалення ресурсу з реєстру його ідентифікатор більше не повинен вважатися гарантованим способом отримання цього ресурсу. Правила повторного використання ідентифікаторів і захисту від застарілих ідентифікаторів мають бути визначені реалізацією підсистеми.

## Структура ResourceInfo

```cpp
struct ResourceInfo {
    ResourceID id;
    ResourceType type;

    uint32_t capabilities;

    Driver::BaseDriver* creator;
    Driver::BaseDriver* maintaner;
};
```

`ResourceInfo` містить метадані зареєстрованого ресурсу.

### Поля

- `id` — ідентифікатор ресурсу в реєстрі. Під час реєстрації його значення встановлює `ResourceSubsystem`.
- `type` — тип ресурсу, визначений значенням `ResourceType`.
- `capabilities` — бітова маска можливостей або властивостей ресурсу.
- `creator` — вказівник на драйвер, який створив і зареєстрував ресурс.
- `maintaner` — вказівник на драйвер, який наразі відповідає за обслуговування ресурсу.

`creator` і `maintaner` описують різні ролі. Вони можуть вказувати на один драйвер або на різні драйвери — залежно від організації системи.

Назва `maintaner` наведена відповідно до поточного коду. Якщо її буде перейменовано на `maintainer`, відповідно потрібно буде оновити й документацію.

### Тип ресурсу

```cpp
enum ResourceType {
    DEVICE,
    SOMETHING_ELSE
};
```

`ResourceType` визначає категорію ресурсу. Наразі перелік типів початковий і має бути розширений відповідно до потреб ядра.

`SOMETHING_ELSE` є тимчасовим значенням із поточної реалізації, а не остаточно визначеним типом ресурсу.

### Можливості ресурсу

Поле `capabilities` призначене для опису властивостей або підтримуваних можливостей ресурсу.

Це метадані, а не набір операцій, які виконує `ResourceSubsystem`. Конкретний драйвер або відповідна підсистема визначає, як використовувати ці можливості.

Формат бітової маски та значення окремих бітів наразі ще не стандартизовані.

## Реєстрація ресурсів

Реєструвати ресурси можуть драйвери. Це відповідає архітектурі драйверної підсистеми, яка допускає роботу з фізичними пристроями, драйверами, побудованими поверх інших драйверів, і суто віртуальними ресурсами.

Для реєстрації використовується функція:

```cpp
ResourceID registerResource(ResourceInfo info);
```

Функція приймає метадані ресурсу, призначає йому ідентифікатор, зберігає запис у реєстрі та повертає отриманий `ResourceID`.

Приклад із поточної реалізації драйвера RAM-диска:

```cpp
Kernel::ResourceSubsystem::ResourceInfo resource{};
resource.type = Kernel::ResourceSubsystem::SOMETHING_ELSE;
resource.capabilities = 0;
resource.creator = this;
resource.maintaner = this;

resourceId =
    Kernel::ResourceSubsystem::registerResource(resource);
```

У прикладі використано `resource{}`, щоб ініціалізувати поля структури нульовими значеннями перед присвоєнням потрібних значень. Тип ресурсу тут умовний і відповідає поточному стану коду.

## Життєвий цикл ресурсу

Життєвий цикл ресурсу визначає драйвер, який ним володіє.

Типовий сценарій:

1. Драйвер створює або готує ресурс.
2. Драйвер реєструє ресурс у `ResourceSubsystem`.
3. Підсистема повертає `ResourceID`.
4. Інші компоненти, яким потрібна спільна ідентифікація, зберігають цей ідентифікатор.
5. Коли ресурс більше не доступний, драйвер видаляє його запис із реєстру.

Для видалення використовується:

```cpp
void unregisterResource(ResourceID id);
```

Важливо розрізняти **видалення запису з реєстру** та **знищення самого ресурсу**. `unregisterResource()` видаляє запис із `ResourceSubsystem`; вона не повинна автоматично знищувати об’єкт ресурсу, звільняти його пам’ять або виконувати специфічні для нього операції.

Якщо драйвер більше не надає відповідний ресурс, він має узгодити його видалення з іншими компонентами, які зберігають його ідентифікатор.

## API

### `registerResource`

```cpp
ResourceID registerResource(ResourceInfo info);
```

Реєструє ресурс і повертає його ідентифікатор.

### `unregisterResource`

```cpp
void unregisterResource(ResourceID id);
```

Видаляє запис ресурсу з реєстру за його ідентифікатором.

### `getResourceList`

```cpp
STDLib::Vector<ResourceID> getResourceList();
```

Повертає список ідентифікаторів ресурсів, зареєстрованих на момент виклику.

### `getType`

```cpp
ResourceType getType(ResourceID id);
```

Повертає тип ресурсу за його ідентифікатором.

### `getCapabilities`

```cpp
uint32_t getCapabilities(ResourceID id);
```

Повертає бітову маску можливостей ресурсу.

### `getCreator`

```cpp
Driver::BaseDriver* getCreator(ResourceID id);
```

Повертає вказівник на драйвер, який створив і зареєстрував ресурс.

### `getMaintaner`

```cpp
Driver::BaseDriver* getMaintaner(ResourceID id);
```

Повертає вказівник на драйвер, який наразі відповідає за обслуговування ресурсу.

### `changeMaintaner`

```cpp
void changeMaintaner(ResourceID id, Driver::BaseDriver* driver);
```

Змінює драйвер, записаний як відповідальний за обслуговування ресурсу.

Ця функція змінює метадані реєстру. Вона сама по собі не передає володіння ресурсом і не виконує процедуру передавання керування між драйверами.

## Взаємодія з іншими підсистемами

Інші підсистеми можуть зберігати `ResourceID` у власних структурах даних, не дублюючи всі метадані ресурсу.

Наприклад, таблиця блокових пристроїв може зберігати ідентифікатор ресурсу, а підсистема ресурсів — надавати інформацію про драйвер, пов’язаний із цим ресурсом.

Таким чином, кожна підсистема зберігає дані, потрібні для її власної роботи, а `ResourceSubsystem` надає спільний механізм ідентифікації.

При цьому `ResourceID` та ідентифікатор драйвера позначають різні сутності: один драйвер може створювати та обслуговувати кілька ресурсів.

## Поточні обмеження та питання для подальшого розвитку

Поточна реалізація є початковою. Перед активним використанням реєстру варто визначити такі правила:

- **Ініціалізація метаданих.** Усі поля `ResourceInfo`, зокрема `capabilities`, мають отримувати визначені значення перед реєстрацією.
- **Вичерпання ідентифікаторів.** Генератор ID має перевіряти переповнення лічильника `nextId`, а не іншої змінної.
- **Повторне використання ID.** Потрібно визначити, чи повертаються звільнені ідентифікатори до пулу, та як запобігати помилковому використанню застарілих ID.
- **Невідомий ID.** Потрібно визначити поведінку функцій доступу, якщо запитаний ресурс відсутній у реєстрі.
- **Час життя драйвера.** Вказівники `creator` і `maintaner` мають залишатися коректними протягом часу, коли їх може використовувати реєстр.
- **Узгодження видалення.** Інші компоненти повинні коректно реагувати на зникнення ресурсу, на який вони посилаються.
- **Типи та можливості.** Перелік типів ресурсів і семантика бітів `capabilities` потребують подальшого визначення.

Ці питання стосуються поточної реалізації та її подальшого розвитку; вони не означають, що `ResourceSubsystem` має перебрати на себе керування ресурсами.

## Підсумок

`ResourceSubsystem` — це реєстр ідентичності та метаданих ресурсів UnityKernel. Він забезпечує спільні `ResourceID` і надає інформацію про зареєстровані ресурси, але залишає створення, функціональність і життєвий цикл ресурсів відповідним драйверам та підсистемам.
