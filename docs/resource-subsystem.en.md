# ResourceSubsystem

## Overview

`ResourceSubsystem` is a kernel subsystem responsible for registering resources, assigning unique identifiers to them, and providing access to their metadata.

A resource is an identifiable entity that can be referenced by multiple kernel components. It may represent a physical device, a virtual device, an abstraction provided by a driver, or another kernel entity that needs a shared identity.

The subsystem acts as a central registry. It does not implement resource-specific operations and does not own the lifecycle of the resources it registers.

## Responsibilities

`ResourceSubsystem` is responsible for:

- Assigning a unique `ResourceID` to each registered resource.
- Storing resource metadata.
- Providing access to registered resource identifiers.
- Providing access to individual resource properties.
- Allowing the recorded maintainer of a resource to be changed.
- Removing resources from the registry when they are unregistered.

The subsystem does not:

- Perform I/O operations on resources.
- Implement device-specific functionality.
- Manage resource-specific operations or capabilities.
- Own the lifecycle of the resource itself.
- Require every kernel subsystem to register its objects as resources.

## Resource Identity

Each registered resource is assigned a `ResourceID`.

```cpp
using ResourceID = int32_t;
```

The identifier is assigned by `ResourceSubsystem::registerResource()` and is used to refer to the resource in the registry.

Other kernel subsystems may store a `ResourceID` in their own tables. This allows their entries to refer to the same resource without duplicating its global identity or depending on the internal representation of the resource registry.

For example, a block-device subsystem may maintain its own block-device table and store a `ResourceID` in each entry. When it needs information about the resource's driver, it can query `ResourceSubsystem`.

A subsystem does not need to use `ResourceSubsystem` if it does not need globally registered resource identities or metadata.

### Identifier lifetime

A `ResourceID` identifies a registered resource, not the resource's storage or implementation directly.

When a resource is unregistered, its identifier must no longer be treated as a valid reference to that resource.

The current implementation uses an integer identifier and maintains a counter for generating new identifiers. The long-term policy for identifier reuse and protection against stale identifiers is not yet defined.

## Resource Metadata

Resource metadata is represented by `ResourceInfo`.

```cpp
struct ResourceInfo {
    ResourceID id;
    ResourceType type;

    uint32_t capabilities;

    Driver::BaseDriver* creator;
    Driver::BaseDriver* maintaner;
};
```

### `id`

The identifier assigned to the resource by `ResourceSubsystem`.

The value supplied to `registerResource()` is replaced with the identifier generated by the subsystem.

### `type`

The general category of the resource, represented by `ResourceType`.

The current enum contains:

- `DEVICE` — a device resource.
- `SOMETHING_ELSE` — a placeholder for other resource categories.

The set of resource types is expected to evolve as the kernel introduces additional resource categories.

### `capabilities`

A 32-bit field describing the resource's capabilities.

The precise capability flags and their semantics are not yet defined. The field is intended to provide metadata about what a resource supports; it does not make `ResourceSubsystem` responsible for implementing those operations.

### `creator`

A pointer to the driver that created and registered the resource.

The creator is responsible for the resource's lifecycle, including deciding when the resource should be removed from the registry.

### `maintaner`

A pointer to the driver currently recorded as responsible for maintaining the resource.

The creator and maintainer may be the same driver, but they represent different roles.

The current API uses the spelling `maintaner`. This name may be corrected to `maintainer` in a future API revision.

## Driver-Managed Resources

Only drivers are permitted to create resources and register them with `ResourceSubsystem`.

The driver architecture supports several kinds of drivers:

1. Drivers that directly manage physical hardware.
2. Drivers that operate on top of other drivers.
3. Drivers that provide virtual functionality without directly controlling physical hardware.

Consequently, a resource is not necessarily a physical device.

A driver may create a virtual resource and expose it through an interface understood by another subsystem. For example, a driver could provide a memory-backed block device that can be consumed through the standard block-device interface.

The resource registry records the resource's identity and metadata. The driver remains responsible for its implementation and lifecycle.

### Resource lifecycle

The lifecycle of a resource is owned by the driver that registered it.

The expected sequence is:

1. A driver creates or initializes a resource.
2. The driver registers the resource with `ResourceSubsystem`.
3. The subsystem assigns a `ResourceID` and stores its metadata.
4. Other components may retain the identifier and query the resource's metadata.
5. When the resource is no longer available, its owning driver unregisters it.

Unregistering a resource removes its registry entry. It does not destroy the underlying resource or release its memory.

The current implementation does not automatically notify other subsystems when a resource is unregistered. Components that retain resource identifiers must account for the possibility that a resource is no longer registered.

## API Reference

### `registerResource`

```cpp
ResourceID registerResource(ResourceInfo info);
```

Registers a resource and returns its assigned identifier.

The identifier is generated by `ResourceSubsystem` and stored in the registered metadata.

If no valid identifier can be allocated, the current implementation invokes `System::panic()`.

### `unregisterResource`

```cpp
void unregisterResource(ResourceID id);
```

Removes the resource identified by `id` from the registry.

This operation removes the metadata entry only. The caller remains responsible for the resource's actual lifecycle.

### `getResourceList`

```cpp
STDLib::Vector<ResourceID> getResourceList();
```

Returns a vector containing the identifiers of currently registered resources.

The returned vector is a separate collection of identifiers, not a view into the registry.

### `getType`

```cpp
ResourceType getType(ResourceID id);
```

Returns the registered resource's type.

### `getCapabilities`

```cpp
uint32_t getCapabilities(ResourceID id);
```

Returns the registered resource's capability bitmask.

### `getCreator`

```cpp
Driver::BaseDriver* getCreator(ResourceID id);
```

Returns the pointer to the driver recorded as the resource's creator.

### `getMaintaner`

```cpp
Driver::BaseDriver* getMaintaner(ResourceID id);
```

Returns the pointer to the driver currently recorded as the resource's maintainer.

### `changeMaintaner`

```cpp
void changeMaintaner(ResourceID id, Driver::BaseDriver* driver);
```

Updates the recorded maintainer of the specified resource.

This changes the metadata in the registry. It does not transfer ownership of the resource or automatically change its operational state.

## Internal Implementation

The current implementation stores resource metadata in:

```cpp
static STDLib::Map<ResourceID, ResourceInfo> resources;
```

The map is private to the `ResourceSubsystem` implementation.

Resource identifiers are generated internally. The implementation also contains a free-identifier collection intended to support identifier reuse.

The registry is implemented in `portable/kernel/cxx/resource.cpp`, while the public declarations are provided by `include/kernel/subsystems/resource.hpp`.

## Current Limitations

The current implementation is an initial version. The following aspects remain to be defined or improved:

- The complete set of resource types.
- The capability flags and their semantics.
- Identifier reuse and stale-identifier protection.
- Behavior when metadata is requested for an invalid or unregistered identifier.
- Coordination with other subsystems when a resource is unregistered.
- The validity of driver pointers if driver unloading is introduced.
- Validation of metadata supplied during registration.

These concerns do not change the subsystem's intended responsibility: maintaining resource identities and metadata while leaving resource-specific behavior and lifecycle management to the responsible drivers.
