# Драйвер AHCI SATA в UnityKernel

У цьому документі описано поточний AHCI-драйвер з опитуванням, підключення
SATA-диска через API блокових пристроїв і наявні обмеження.

## Реалізовано

Драйвер ядра в `portable/drivers/cxx/ahci/ahci.cpp`:

- Переглядає PCI configuration space та знаходить перший AHCI-контролер
  (клас `01:06:01`), вмикає PCI memory-space і bus-master доступ.
- Перевіряє та визначає розмір 32-бітного memory BAR5 (ABAR). Поточне ядро
  використовує адресу BAR напряму; paging і загальний механізм MMIO-відображень
  поки не реалізовані.
- За потреби виконує передачу керування від BIOS операційній системі, скидає
  HBA, вмикає режим AHCI та вимикає переривання HBA, оскільки команди
  обробляються опитуванням.
- Знаходить реалізований порт з активним з'єднанням і пробує виконати ATA
  `IDENTIFY DEVICE`. Це також працює з контролерами на кшталт QEMU, які
  повідомляють про активне з'єднання раніше, ніж надають коректне значення
  `PxSIG`. SATAPI та інші пристрої без підтримки ATA відхиляються, якщо команда
  ідентифікації завершується помилкою.
- Виділяє вирівняні буфери списку команд, отриманих FIS і таблиці команд у
  heap ядра, налаштовує порт і надсилає ATA IDENTIFY DEVICE.
- Вимагає LBA48 і логічні сектори по 512 байтів. Диски з іншим розміром
  логічного сектора відхиляються, оскільки `BlockdevDriver` наразі працює з
  секторами по 512 байтів.
- Реалізує READ DMA EXT і WRITE DMA EXT з опитуванням та обмеженим часом
  очікування. Один запит обмежено 8192 секторами (4 MiB), а публічний API
  блокового пристрою обмежує LBA та місткість 32 бітами.
- Надає вибраний диск як `Driver::AHCI::AHCIDriver` — реалізацію
  `BlockdevDriver` з методами `read(lba, buffer, count)`, `write(...)`,
  `sectors()` і `portNumber()`.

Драйвер додається до списку та ініціалізується під час запуску ядра. Якщо
придатного AHCI SATA-диска немає, ядро виводить попередження і продовжує
роботу. Наявний FAT32 RAM-диск залишається окремим: SATA-диск автоматично не
монтується й не форматується.

## Використання блокового пристрою

Менеджер драйверів завантажує AHCI-пристрій під час `kernelMain()`. Код, що
має доступ до драйвера, може користуватися звичайним API блокового пристрою:

```cpp
#include <drivers/ahci/ahci.hpp>
#include <kernel/subsystems/driver.hpp>

auto* disk = static_cast<Driver::AHCI::AHCIDriver*>(
    Kernel::DriverSubsystem::loadDriver(Driver::Category::BLK, Driver::Type::AHCI));

uint8_t sector[Driver::Blockdev::sectorSize];
if (disk != nullptr && disk->read(0, sector, 1)) {
    // Сектор 0 прочитано.
}

// Запис відбувається лише за явним викликом; під час старту диск не форматується.
if (disk != nullptr && disk->write(10, sector, 1)) {
    // Сектор 10 записано.
}
```

Перед введенням-виведенням перевіряйте `sectors()` і вважайте `false`
ознакою помилки I/O. Один запит може передавати до 4 MiB. Більші запити
розділяйте на кілька викликів і перевіряйте результат кожного. Не тестуйте
запис на реальному диску — використовуйте тимчасовий образ QEMU.

## Запуск з SATA-диском у QEMU

Створіть тимчасовий raw-образ:

```sh
qemu-img create -f raw sata-test.img 64M
```

Зберіть ISO за інструкціями Docker у `README.md`, а потім запустіть його з
емулятором AHCI та диском:

```sh
qemu-system-x86_64 \
    -cdrom out/kernel.iso \
    -drive if=none,id=sata0,file=sata-test.img,format=raw \
    -device ahci,id=ahci \
    -device ide-hd,drive=sata0,bus=ahci.0 \
    -serial stdio
```

Під час старту ядро має повідомити вибраний порт AHCI та кількість секторів.
Команди FAT32 оболонки й надалі працюють з RAM-диском; сектори SATA доступні
через `AHCIDriver`, але ще не змонтовані як файлова система.

## Важливі обмеження

- Доступний лише перший PCI-контролер AHCI і перший придатний SATA-диск на
  ньому. SATAPI, port multiplier, кілька дисків і PCI IDE compatibility mode
  не підтримуються.
- Використовується PCI configuration mechanism 1 (`0xCF8`/`0xCFC`).
  PCIe ECAM не реалізований.
- Реалізація призначена для поточної 32-бітної конфігурації x86. DMA-адреси
  дорівнюють значенням вказівників, бо ядро наразі працює без paging і
  використовує RAM з identity addressing. Буфери DMA та буфери виклику мають
  бути суцільними й повністю розташованими нижче 4 GiB. Перед увімкненням
  paging це припущення потрібно замінити явним відображенням
  virtual-to-physical і DMA-алокатором.
- Для кожного запиту використовується лише один запис PRDT; запити понад
  4 MiB відхиляються.
- Команди виконуються опитуванням з тайм-аутом у кількості ітерацій, а не
  каліброваним часом. Немає переривань завершення, повторних спроб,
  hotplug, політики кешування чи деталізованих повідомлень про помилки.
- Потрібна підтримка LBA48. Публічний API блокового пристрою використовує
  32-бітні LBA та кількість секторів, тому диски, більші за доступний цим API
  діапазон, доступні лише частково.
- Немає розбору таблиці розділів, монтування SATA-файлової системи чи
  автоматичного форматування. Невдалий запис усе одно може змінити вміст
  носія; перед записом викликач має обрати правильний розділ і файлову систему.

## Наступні кроки

1. Додати PCI-підсистему та належне відображення пам'яті для BAR замість
   прямого розіменування фізичної адреси ABAR.
2. Додати DMA-алокатор, що повертає і virtual-, і physical-адреси, враховує
   межі 4 GiB та можливості HBA і гарантує когерентність кешу.
3. Надавати кожен SATA-диск як окремий блоковий пристрій і підтримати кілька
   контролерів.
4. Покращити повідомлення про тайм-аути й помилки, відновлення портів і
   додати цільові тести для розбору IDENTIFY, меж LBA та побудови PRDT.
5. Додати пошук розділів і явне монтування вибраного SATA-тома; не пов'язувати
   монтування чи форматування з ініціалізацією драйвера.
6. Додати переривання лише після підготовки маршрутизації переривань та
   життєвого циклу обробників.
