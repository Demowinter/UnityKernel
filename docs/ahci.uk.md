# Основи драйвера AHCI в UnityKernel

У цьому документі описано початкову підтримку AHCI, поточний API для
перевірки контролера, його обмеження та наступні кроки для читання й запису
на SATA-диски.

## Поточна підтримка

Початкова реалізація містить описи регістрів AHCI Host Bus Adapter (HBA) та
невеликий клас для перевірки контролера:

- `include/drivers/ahci/ahci.hpp` описує глобальні регістри HBA, блоки
  регістрів 32 портів та потрібні розміри структур.
- `portable/drivers/ahci/ahci.cpp` перевіряє передану область відображених
  регістрів, читає бітову маску реалізованих портів, рахує їх і визначає тип
  підключеного пристрою за SATA-сигнатурою.
- Джерело додається до цілі ядра.

Контролер поки що не шукає PCI-пристрої, не відображає ABAR, не змінює
налаштування контролера, не виділяє DMA-буфери, не надсилає команди й не
реалізує читання та запис блокового пристрою. Драйвер AHCI ще не зареєстровано
у шарі файлової системи чи блокових пристроїв.

## Використання для перевірки контролера

Спочатку викликач має знайти PCI-контролер AHCI та відобразити його ABAR
(зазвичай BAR5) у адресний простір ядра. Передайте відображену, некешовану
MMIO-область і її розмір до `Controller::initialize()`:

```cpp
#include <drivers/ahci/ahci.hpp>

Driver::AHCI::Controller controller;
if (controller.initialize(mappedHbaRegisters, mappedSize)) {
    const uint32_t portMask = controller.implementedPortMask();
    const uint32_t portCount = controller.implementedPortCount();

    for (uint8_t port = 0; port < Driver::AHCI::portCount; ++port) {
        switch (controller.portType(port)) {
            case Driver::AHCI::PortType::SATA:
                // На цьому реалізованому порту присутній SATA-пристрій.
                break;
            case Driver::AHCI::PortType::SATAPI:
                // Присутній пристрій ATAPI.
                break;
            default:
                break;
        }
    }
}
```

`initialize()` лише зберігає переданий вказівник після перевірки, що він
ненульовий, належно вирівняний і що область містить повний опис регістрів
HBA. Метод покладається на те, що викликач уже створив коректне MMIO-відображення.
Поля регістрів HBA та портів оголошено як `volatile`, оскільки вони відповідають
апаратним регістрам. `portRegisters()` повертає `nullptr`, якщо контролер не
ініціалізовано, номер порту поза діапазоном або порт відсутній у бітовій масці
реалізованих портів HBA.

Класифікація порту вимагає активного з'єднання зі статусом виявлення пристрою
`3` і статусом живлення інтерфейсу `1`. Сигнатура визначає SATA, SATAPI,
enclosure-management bridge або port multiplier. Це лише поточний знімок
регістрів стану, а не гарантія, що з'єднання залишиться активним.

## Безпека та межі реалізації

Не передавайте фізичну адресу PCI BAR напряму, якщо її ще не відображено й
ядро не може звертатися до неї. У поточному 32-бітному ядрі немає загального
механізму відображення фізичної пам'яті, переліку PCI configuration space чи
алокатора DMA-адрес. Списки команд AHCI, область отриманих FIS і буфери даних
мають бути доступні для DMA за фізичними адресами, які записуються в
контролер; звичайні віртуальні адреси ядра автоматично для цього не підходять.

Поточний інспектор не записує в регістри HBA, тому він не скидає контролер і
не змінює налаштування прошивки. Не додавайте реальне введення-виведення,
доки не будуть готові MMIO-відображення, DMA-пам'ять та обробка тайм-аутів і
помилок.

## Рекомендований план реалізації

### 1. Додати пошук PCI та відображення BAR

Реалізуйте доступ до PCI configuration space і пошук пристроїв із кодом класу
AHCI: базовий клас `0x01`, підклас `0x06`, інтерфейс програмування `0x01`.
За потреби ввімкніть memory-space і bus-master доступ, перевірте BAR5,
визначте його розмір і відобразіть як некешований MMIO. Передайте відображену
область до `Controller::initialize()`.

### 2. Додати безпечне для DMA виділення пам'яті

Забезпечте виділення пам'яті з вирівнюванням за сторінкою, відомими фізичними
адресами та потрібним вирівнюванням структур. Дотримуйтеся обмежень ширини
адрес, оголошених можливостями HBA та режимом DMA контролера. Розрізняйте
віртуальні й фізичні адреси та резервуйте пам'ять, поки команди активні.

### 3. Ініціалізувати порт і реалізувати IDENTIFY

Для кожного реалізованого SATA-порту:

1. Перевірте стан з'єднання та сигнатуру пристрою.
2. Зупиніть обробку команд і FIS та дочекайтеся завершення з обмеженим
   тайм-аутом.
3. Виділіть і налаштуйте список команд, область отриманих FIS і таблицю команд.
4. Запустіть порт і надішліть ATA IDENTIFY DEVICE.
5. Розберіть місткість і підтримувані режими адресації; перевіряйте завершення
   команди та помилки task-file.

Спочатку використовуйте опитування й вимкнені переривання. Додайте завершення
команд через переривання лише після того, як IDT і маршрутизація переривань
ядра зможуть безпечно обробляти контролер.

### 4. Реалізувати читання та запис блоків

Реалізуйте обмежені ATA DMA-команди, спочатку READ DMA EXT і WRITE DMA EXT,
якщо вони підтримуються пристроєм. Перевіряйте арифметику LBA/кількості
секторів, розмір буфера, стан порту та місткість пристрою. Явно обробляйте
тайм-аути, помилки task-file та часткові помилки. Після цього надайте диск
через реалізацію `BlockdevDriver`.

### 5. Інтегрувати й тестувати

Реєструйте блокові пристрої AHCI лише після того, як введення-виведення
командами працюватиме. Тестуйте на контролері AHCI у QEMU з тимчасовими
образами дисків. Перевірте випадки відсутності диска, непідтримуваного
пристрою, некоректних можливостей, тайм-ауту та помилок введення-виведення.
Відокремте перегляд регістрів від виконання команд, щоб тестувати розбір і
перевірки без реального обладнання.
